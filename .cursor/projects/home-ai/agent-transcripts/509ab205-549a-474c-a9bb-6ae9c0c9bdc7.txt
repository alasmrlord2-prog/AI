# 1️⃣ إنشاء المستخدم داخل CRM (User Creation)

## ✅ As-Is (الحالي)

* CRM ينشئ User
* status افتراضي `pending`
* ممكن تفعّله مباشرة من CRM
* email_verified يُمرّر من الطلب
* ربط Tenant يتم مباشرة

### ❗ Problems

1. **CRM يقرر التفعيل** ❌
   (خطر أمني + كسر مبدأ zero-trust)
2. لا يوجد **invitation flow**
3. `email_verified` يمكن تزويره من API

---

## 🌍 Best Practice عالمي (To-Be)

### 🥇 Golden Rule:

> **أي User يُنشأ من CRM = Invited, NOT Active**

### User States الصحيحة:

```txt
invited → email_verified → active → suspended
```

---

## 🔧 التعديل المقترح (Minimal Impact)

### 1️⃣ غيّر منطق CRM:

```diff
- if user_data.status == "active":
-    user.status = "active"
-    user.email_verified = user_data.email_verified

+ user.status = "invited"
+ user.email_verified = False
```

### 2️⃣ أضف Invitation Token:

```txt
user_invitations
- id
- user_id
- tenant_id
- token
- expires_at
- accepted_at
```

### 3️⃣ Endpoint جديد:

```http
POST /api/auth/accept-invitation
```

### Verification = **Flows وليس Flags**

# 4️⃣ كيف نطبّق AAA (Best Practice عالمي)

## 🔐 A) Authentication – التحقق من الهوية

### ✅ الممارسة الأفضل (Recommended Stack)

**Hybrid Authentication**

### 🔹 ماذا نستخدم؟

* **JWT (Access Token)**

  * قصير العمر: `15–30 دقيقة`
* **Refresh Token**

  * طويل العمر
  * محفوظ كـ `httpOnly secure cookie`
* **Optional External IdP**

  * Keycloak / Auth0 / Azure AD (Enterprise)

---

### 🔹 Flow معتمد:

```text
Login
→ Validate credentials
→ Issue Access JWT
→ Issue Refresh Token
→ Attach tenant_id + role_id داخل JWT
```

### 🔹 JWT Payload (مهم):

```json
{
  "sub": "user_id",
  "tenant_id": "org_123",
  "role": "admin",
  "permissions_version": 3,
  "exp": 123456789
}
```

📌 **ليش permissions_version؟**
حتى تقدر تبطل صلاحيات User بدون ما تنتظر انتهاء التوكن.

---

## 🛂 B) Authorization – الصلاحيات

### ✅ المعيار الذهبي:

**RBAC + Fine-Grained Permissions**

---

### 🔹 Structure:

```txt
User → Role → Permissions
```

### 🔹 Models:

```txt
roles
- id
- name (owner, admin, analyst, viewer)

permissions
- id
- key (view_dashboard, run_query, export_data)

role_permissions
```

---

### 🔹 Runtime Enforcement:

* **Backend**: mandatory
* **Frontend**: UX only (ليس أمان)

```python
@require_permission("run_query")
def query_logs():
    ...
```

❌ ممنوع:

* isAdmin flags
* hardcoded roles

---

## 📊 C) Accounting – تسجيل الاستهلاك (الأهم في SaaS)

### ✅ Best Practice عالمي:

**Event-Based Accounting (Usage Events)**

---

### 🔹 ماذا نسجل؟

أي Action له قيمة:

| Action        | Units  |
| ------------- | ------ |
| API call      | 1      |
| SIEM query    | 5      |
| Log ingestion | per MB |
| Export        | 10     |

---

### 🔹 Usage Event Schema:

```txt
usage_events
- id
- tenant_id
- user_id
- service
- action
- units
- source (api / ui)
- timestamp
```

---

### 🔹 Flow:

```text
User Action
→ Emit Usage Event
→ Queue (async)
→ Metering Worker
→ Aggregate usage
```

📌 **ممنوع تحسب usage synchronously** (يضرب الأداء)

* MFA changes
* Role / Permission changes

* Export
* Bulk delete
* Sensitive queries

## 🔹 Audit Log Schema:

```txt
audit_logs
- id
- tenant_id
- actor_user_id
- action
- target_type
- target_id
- ip_address
- user_agent
- metadata (JSON)
- timestamp
```

---

### 🔹 Example:

```json
{
  "action": "ROLE_CHANGED",

  "old_role": "viewer",

}
```
