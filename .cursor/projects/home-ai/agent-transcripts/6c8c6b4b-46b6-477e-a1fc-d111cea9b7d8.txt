## ⚠️ نقاط لازم تتأكد منها (حتى يكون Enterprise-grade)

### A) Invitation Token: تخزينه وإدارته

**أهم سؤال:** هل تخزّن `invitation_token` **خام** في DB ولا **hash**؟

* الأفضل عالميًا: تخزن **token_hash** فقط (مثل reset password tokens)
* إذا DB انكشفت، ما حدا يقدر يستخدم tokens مباشرة

✅ To-do سريع:

* `token_hash = sha256(token + server_secret)`
* قارن hash عند القبول
* وخلي token نفسه يظهر مرة واحدة فقط وقت الإنشاء

**وكمان لازم:**

* `expires_at` إلزامي
* `accepted_at` إلزامي + منع إعادة الاستخدام
* invalidation عند إصدار دعوة جديدة لنفس user/tenant (اختياري بس مفيد)

### B) accept-invitation: كلمة المرور “اختيارية” خطرة

ذكرت إن endpoint قبول الدعوة يقبل `password` اختياريًا.

هاي ممكن تفتح سيناريوهات خطرة:

* user يصير `active` بدون ما يثبت كلمة مرور
* أو يبقى على password مؤقت/ضعيف

✅ Best practice:

* إذا المستخدم **ما عنده password مضبوط** → اجعل `password` **مطلوب**
* أو اعمل حالتين واضحين:

  1. **Invited existing user** (عنده حساب مسبق) → ما يحتاج password
  2. **Invited new user** → لازم set password + policy

**نصيحة قوية:** اربط القبول بـ:

* `email_verified = true`
* `status = active`
* `tenant_user.status = active`
  في transaction واحد

### D) Tenant enforcement: انتبه للـ “public endpoints”

إذا شدّدت AAA tenant enforcement، تأكد ما تكسر endpoints لازم تكون بدون tenant، مثل:

* `/auth/login`

* `/health`
* `/docs`

✅ Best practice:

* allowlist مسارات “tenantless”
* وباقي المسارات لازم `tenant_id` بشكل إلزامي

### E) Usage Events: بدك Idempotency + Correlation

إذا بدأت تسجّل events، لازم تمنع التكرار خصوصًا لو في retries.

✅ إضافات مهمة جدًا:

* `correlation_id` (تستخدمه كمان بالـ audit)

**وأفضل:**

* batch insert للأحداث (لو traffic عالي)
* async queue لاحقًا

### F) permissions_version: لازم “مصدر الحقيقة”

* الـ middleware يرفض token إذا claim أقدم من DB

✅ Tip:

* خليه per-tenant membership (لأن user ممكن يكون admin في tenant A و viewer في B)

## ⚠️ نقاط لازم تتأكد منها (هاي هي “الفروقات الصغيرة” اللي بتعمل مشاكل كبيرة)

### A) هل صار فعلاً سلوك الـ Refresh موحّد؟

لا يكفي ترجع `refresh_token`… لازم تتأكد من:

* **Refresh token rotation** (يفضل)
* تخزين refresh token (hash) بالـ DB / session store
* invalidate عند الاستخدام إذا بتعمل rotation

✅ Checklist:

* refresh token له `jti` أو `token_id`
* عند refresh: يتم إنشاء refresh جديد + إبطال القديم
* عند logout: إبطال session → كل tokens تبعها تبطل

---

### B) MFA ما لازم ينحكى عنه “requires_mfa” فقط

طالما عندك `requires_mfa=True`… ممتاز كبداية، لكن لازم تدقق:

* هل المستخدم يأخذ **أي توكن صالح** قبل إتمام MFA؟

  * إذا نعم → خطر (لازم ما تعطي توكن صالح قبل MFA)
  * إذا لا → تمام

✅ Best practice:

* عند `requires_mfa=True`:

  * لا ترجع access/refresh صالحين
  * ارجع `mfa_ticket` قصير العمر
  * ثم endpoint: `/api/auth/mfa/verify` يعطي tokens بعد التحقق

---

### C) tenant selection لازم يكون محدد وواضح

في `/auth/login` كان يختار أول tenant membership.
في `/identity/login` كان يتطلب tenant_id (حسب وصفك سابقًا).

الآن بعد التوحيد الجزئي، تأكد من سيناريو:

* user عضو في أكثر من tenant
* login بدون tenant_id

✅ Best practice:

* إذا user عنده أكثر من tenant:

  * ترجع `requires_tenant_selection: true` + قائمة tenants (مختصرة)
  * أو تطلب tenant_id صراحة

---

### D) SessionManager: انتبه لمضاعفة الـ sessions

إذا صار عندك مسارين ينشئوا sessions، تأكد أنه ما عم تعمل:

* session جديد لكل login attempt فاشل
* session جديد قبل اكتمال MFA
* session جديد مع refresh بدل تحديث/rotate

✅ المطلوب:

* session ينشأ فقط عند نجاح الدخول النهائي (بعد MFA إن وجدت)
* refresh لا ينشئ session جديد، فقط يدوّر tokens داخل نفس session (حسب تصميمك)

## ✅ أول شي كمّل: Invitation Hardening (أعلى ROI وأقل خطر)

### ليش؟

لأن Invitation هو “باب الدخول” لأي user جديد، وبـ B2B/Public لازم يكون **غير قابل للسرقة أو إعادة الاستخدام**.

### المطلوب عالميًا

1. **ما تخزّن token خام** في DB
   خزّن `token_hash` فقط
2. **Single-use + expiry صارم**
3. **قبول الدعوة = Transaction واحدة**
4. **Password policy** واضح (مهم جدًا لـ Public)

### DB / Model

بدّل جدول `user_invitations` ليصير مثل:

```txt
user_invitations
- id
- tenant_id
- user_id
- token_hash (unique index)
- expires_at
- accepted_at (nullable)
- created_at
- created_by_user_id (optional)
- revoked_at (optional)
```

### Token hashing (اقتراح عملي)

* generate token (random 32 bytes base64url)
* hash = sha256(token + server_secret)

> ميزة: حتى لو DB انسرقت، ما في “tokens جاهزة” للاستخدام.

### accept-invitation (قواعد سلوك)

* إذا user ما عنده password مضبوط → **password required**
* عند القبول:

  * `user.email_verified = true`
  * `user.status = active`
  * `tenant_user.status = active`
  * `accepted_at = now`
  * (optional) revoke أي invitations أخرى لنفس user/tenant

### اختبارات لا تتنازل عنها

* token منتهي → 400/401
* token مستخدم → 409
* token غلط → 401
* race condition: قبولين بنفس اللحظة → واحد ينجح والثاني يفشل (unique/lock)

## 3) Refresh Token Rotation (حماية من token theft)

**المبدأ:** كل refresh token ينستخدم مرة واحدة.

* refresh endpoint:

  * validates refresh token + session
  * يصدر refresh جديد
  * يبطل القديم

**لا تنشئ session جديدة عند refresh**. حافظ على نفس session_id.

**اختبارات:**

* reuse refresh القديم → 401
* refresh بعد logout/session revoke → 401

---

## 4) permissions_version Enforcement الحقيقي

أنت ضفت claim — ممتاز. هلا فعّله:

* خليه per tenant membership:

  * `tenant_users.permissions_version`
* عند تغيير role/permissions:

  * increment version
* في middleware:

  * إذا `token.permissions_version < db.permissions_version` → 401 re-auth

> هيك بتقدر تعمل revoke صلاحيات “فوري” بدون انتظار انتهاء JWT.

---

## 5) Usage Events Idempotency + Correlation (للـ Public API)

بما إن عندك event-based accounting بالتوازي:

أضف:

* `request_id` (من header مثل `X-Request-Id` أو تولده بالـ middleware)
* `correlation_id` موحّد (نفسه للـ audit + usage)
* unique index على `request_id` داخل `usage_events`

> هذا يمنع double-charging إذا صار retry من العميل أو timeout.
